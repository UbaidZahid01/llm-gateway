The LLM Gateway, explained from zero

A safety checkpoint that sits between your app and the big AI providers. Your code talks to it exactly like it talks to OpenAI — but every message is scanned, cleaned, routed, and recorded on the way through.

FastAPI backend React + Streamlit admin UIs OpenAI · Anthropic · Qwen JSON-file storage

01 What this thing is

Imagine a security desk in the lobby of a building. Everyone who wants to talk to the AI has to walk past the desk. Nobody gets to skip it. That desk is this gateway.

Normally an app sends its prompts straight to OpenAI (or Claude, or Qwen). That's fast, but nobody is checking what leaves the building. Someone could paste a customer's credit card number, a password, or a secret API key into a prompt — and it would sail off to a third party with no record and no filter.

This project puts a gateway in the middle. Your app sends its request to the gateway instead of to the AI. The gateway then:

  • Checks who you are — every developer has their own key.
  • Cleans the message — finds sensitive info (emails, cards, secrets…) and hides, masks, or blocks it before it reaches the AI. These filters are called guardrails.
  • Sends it to the right AI provider — and translates the request so OpenAI, Claude, and Qwen all "just work."
  • Cleans the AI's answer too — the reply is scanned on the way back.
  • Writes down everything — every request and response is saved to an audit log.

The clever part: the gateway speaks the exact same "language" as OpenAI's API. So a developer can take their existing OpenAI code, change one line (the address it points at), and everything keeps working — now with guardrails and logging for free.

The three pieces of this repo

backend/ — the actual gateway (Python / FastAPI). This is the brain. Everything important happens here.

frontend/ — a React admin website for humans: create developers, edit the safety rules, browse the logs.

streamlit_ui/ — a simpler, single-file admin console that does the same things plus a "try a live call" tester.

03 Words you'll keep seeing

Learn these nine words and the rest of the doc reads easily.

WordIn plain English
GatewayThe middle-man server. Your app talks to it instead of talking to the AI directly.
Provider / VendorThe company that actually runs the AI: openai, anthropic, or qwen.
DeveloperA person (with an app) who is allowed to use the gateway. Each one is registered and gets their own key.
API keyA secret password string. Developers get one starting sk-guard-…; admins share one X-Admin-Key.
Provider keyThe developer's own OpenAI/Anthropic/Qwen key, sent per call in the X-Provider-Key header. The gateway holds none of its own.
GuardrailA safety filter that looks for sensitive text and decides what to do with it.
PII"Personally Identifiable Information" — private data like emails, phone numbers, credit cards, SSNs.
PolicyThe rulebook: for each kind of PII, what should the gateway do? One global rulebook for the whole system.
Audit logThe permanent record of every call — who called, what they sent, what came back, how long it took.

The four things a guardrail can do

Every rule ends in one of these four actions. You'll see them everywhere:

allow — let it through untouched mask — hide most of it, e.g. *******1234 redact — replace it with a tag, e.g. [REDACTED_EMAIL] block — stop the whole request cold

04 Life of one request

This is the heart of the system: what happens, step by step, when a developer's app calls /v1/call_llm. The code for this lives in backend/src/routers/llm.py.

Sequence of a single call_llm request
%%{init: {'theme':'neutral'}}%%
sequenceDiagram
    autonumber
    participant App as Developer's app
    participant GW as Gateway
    participant AI as AI Provider
    participant Log as Audit log

    App->>GW: POST /v1/call_llm + Bearer key
    GW->>GW: Verify key (who is this?)
    GW->>GW: Rate limit — under the per-minute cap?
    GW->>GW: Interceptor: scan & clean the prompt
    alt Blocked (e.g. credit card found)
        GW->>Log: record the blocked attempt
        GW-->>App: 403 guardrail_blocked
    else Allowed / cleaned
        GW->>AI: forward the cleaned request
        AI-->>GW: AI's answer
        GW->>GW: Processor: scan & clean the answer
        GW->>Log: record request + response + findings
        GW-->>App: 200 OK — OpenAI-shaped reply
    end

The same story, as a checklist

  1. Identify the caller. The request must carry Authorization: Bearer sk-guard-…. The gateway hashes that key and looks it up in keys.json. No match → 401, done.
  2. Rate limit. Has this developer made too many calls this minute? If yes → 429 with a Retry-After header. (Default: 60/min. See section 09.)
  3. Choose the provider. The gateway reads the optional provider field in the body. If it's missing, it falls back to the developer's registered vendor. Unknown provider → 400.
  4. Interceptor (clean the request). The guardrail engine scans every message. It masks/redacts sensitive spans in place. If any rule says block (or a denylisted word appears) → 403, and the request never reaches the AI. The offending value is still redacted before it's logged, so raw secrets never hit disk.
  5. Forward to the AI. The gateway builds a fresh provider client using the key from the caller's own X-Provider-Key header — it never has one of its own — and calls the real AI, returning an OpenAI-shaped answer. No key for the chosen provider → 400 provider_key_missing.
  6. Processor (clean the response). The same engine runs on the AI's reply. If a block rule fires here, the text is swapped for a "withheld by policy" notice instead of being shown.
  7. Log everything. A full record — including which provider served it, the guardrail findings, the status code, and the latency in milliseconds — is appended to audit_logs.json (and optionally pushed to an external sink).
  8. Reply. The developer's app gets back a response in the exact shape OpenAI would have sent.
Why this matters

Because the gateway copies OpenAI's request and response format precisely, a developer can point the official OpenAI SDK at it and change nothing else in their code. All the safety and logging is invisible to them.

05 Every endpoint

There are six endpoints in total, in three groups. The base address is http://localhost:8000 when running locally.

The gateway endpoint (for developers)

This is the one developers' apps actually call. It's protected by the developer's personal Bearer key.

POST /v1/call_llm Bearer key

Send a chat request; get a chat answer. The body is identical to OpenAI's chat.completions.create — model, messages, tools, temperature, response_format, and so on. One extra optional field, provider, lets you pick the AI vendor per call; it's stripped out before forwarding. The gateway holds no provider keys of its own, so every call must also carry your own key for that provider in an X-Provider-Key header.

Example request

# curl — note the address is the gateway, not OpenAI
curl http://localhost:8000/v1/call_llm \
  -H "Authorization: Bearer sk-guard-YOUR_DEV_KEY" \
  -H "X-Provider-Key: sk-YOUR_OWN_OPENAI_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "provider": "openai",
    "model": "gpt-4o-mini",
    "messages": [{"role": "user", "content": "Say hello in 5 words"}]
  }'

Or with the OpenAI SDK — same code, new address

from openai import OpenAI

client = OpenAI(
    api_key="sk-guard-YOUR_DEV_KEY",       # the key the gateway gave you
    base_url="http://localhost:8000/v1",   # point at the gateway
    default_headers={"X-Provider-Key": "sk-YOUR_OWN_OPENAI_KEY"},
)
resp = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "Say hello in 5 words"}],
)

Possible responses

StatusMeaning
200Success — an OpenAI-shaped chat.completion reply.
400Bad request — unknown provider, missing provider key, or streaming (not supported yet).
401Missing or wrong Bearer key.
403Blocked by guardrails — a block rule or denylisted term fired.
429Rate limit exceeded — wait for the Retry-After seconds.

Admin endpoints (for managing the system)

These live under /admin and are protected by the admin key (X-Admin-Key header). Code: backend/src/routers/admin.py.

POST/admin/developersX-Admin-Key

Register a new developer and mint their key. Send { name, designation, vendor }. You get back their emp_id and the raw api_key — shown only this once. Only a hash is stored, so it can never be retrieved again.

GET/admin/developersX-Admin-Key

List all registered developers (newest first). Shows a short key prefix only — never the full key.

GET/admin/policyX-Admin-Key

Read the single global guardrail rulebook — the PII rules, the denylist, and the request/response switches.

PUT/admin/policyX-Admin-Key

Replace the rulebook. Missing fields are filled from the sensible default, so a partial update is safe.

Audit endpoints (for reviewing history)

Under /audit, also protected by the admin key. Code: backend/src/routers/audit.py.

GET/audit/logsX-Admin-Key

List every recorded call, newest first. Optional filters: ?emp_id=EMP-0001 and/or ?vendor=openai.

GET/audit/logs/{log_id}X-Admin-Key

Fetch one full record by its log_id. Returns 404 if that id doesn't exist.

Plus one free health check

GET/healthno auth

Returns {"status": "ok"}. Handy for "is the server up?" checks.

Interactive docs come for free

FastAPI auto-generates a live, clickable API explorer at http://localhost:8000/docs (Swagger UI) once the server is running. Great for poking at endpoints without writing code.

06 Guardrails explained

This is the safety brain. It runs twice per call — once on the way in (the interceptor) and once on the way out (the processor) — using one shared engine in backend/src/guardrails.py.

Step 1 — Detectors find the sensitive stuff

The file backend/src/detectors.py holds regex patterns that scan text for known kinds of private data. Each has a priority so, for example, a credit-card number is never mistaken for a phone number.

TypeWhat it catchesNote
secretAPI keys / tokens (sk-…, AWS AKIA…, GitHub ghp_…, Slack xox…)Highest priority
credit_card13–19 digit card numbersConfirmed with the Luhn checksum, so random digits don't false-alarm
cnicPakistani national ID (#####-#######-#)
ssnUS Social Security number (###-##-####)
ipIPv4 addresses
emailEmail addresses
phonePhone numbersLowest priority

The comment in the code notes this is a "regex baseline" — a heavier engine like Microsoft Presidio could be dropped in behind the same detect() function without changing anything else.

Step 2 — The policy decides what to do

For each type it finds, the engine looks up the action in the policy (backend/src/policy.py). The starting defaults are:

TypeDefault action
email, phoneredact
ipmask
credit_card, ssn, cnic, secretblock

There's also a denylist — a list of forbidden words or regex patterns. If any appears, the whole request is blocked, no matter what else is in it. And two master switches, apply_to_request and apply_to_response, can turn either scanning pass off entirely.

How the engine decides, per piece of text
%%{init: {'theme':'neutral', 'flowchart':{'curve':'basis'}}}%%
flowchart LR
    T["A message"] --> DL{"Denylisted
word?"}
    DL -- yes --> B["🚫 BLOCK
whole request"]
    DL -- no --> D["Run detectors"]
    D --> A{"Action for

    A -- allow --> KEEP["leave as-is"]

Privacy detail worth knowing

The audit log records findings as type + action + count only — e.g. "1 email, redacted." It never stores the raw sensitive value. Even when a request is blocked, the detected value is redacted before the payload is written to disk. Secrets never land in the log.

You don't have to edit JSON by hand — the Guardrail Policy page in the React UI (or the Policy tab in Streamlit) lets you flip actions and manage the denylist with dropdowns.

07 Providers & routing

The gateway can talk to three different AI companies, and it hides their differences so callers only ever deal with OpenAI's format. Code: backend/src/providers/.

How the provider is chosen for a given call:

  1. If the request body has a provider field, use that.
  2. Otherwise, fall back to the vendor the developer was registered with.
  3. If that provider name isn't one of the three known ones → 400 provider_not_supported.
ProviderHow it worksKey
openaiStraight pass-through — the gateway's format is OpenAI's, so nothing to translate.Caller's own, via X-Provider-Key
anthropicTranslates the OpenAI request into Anthropic's Messages API (system prompt, tools, tool choice) and maps the answer back to OpenAI's shape.Caller's own, via X-Provider-Key
qwenAlibaba's Qwen via DashScope, which already speaks OpenAI's format — so it reuses the OpenAI adapter with a different address.Caller's own, via X-Provider-Key

Each provider is a small "adapter" implementing one method: call(body) → openai_shaped_response. They all share the base class in providers/base.py. None of them hold a key of their own — get_provider(name, api_key) builds a fresh adapter per call from whatever the caller sent in X-Provider-Key. Send no key (or the wrong header) and you get a clear 400 provider_key_missing — not a mysterious crash.

Registered vendor vs. actual provider

The audit log stores both: vendor is the developer's registered default, and provider is who actually served that specific call. They can differ when a caller overrides the provider per request.

08 Where everything is stored

There is no database. Everything is plain JSON files in one folder: backend/db_json/. Simple to read, simple to back up, simple to inspect. The read/write helper is backend/src/storage.py.

FileWhat's inside
employees.jsonDeveloper records: emp_id, name, designation, vendor, created date.
keys.jsonOne entry per key: which developer, vendor, a hash of the key (never the raw key), and a short prefix for display.
audit_logs.jsonThe big one — every single call_llm request/response pair with guardrail findings, status, and latency.
guardrail_policy.jsonThe one global rulebook. Auto-created with sensible defaults the first time it's needed.

So — "where are the logs?"

Two places, and the second is optional:

  1. On disk, always. Every call is appended to backend/db_json/audit_logs.json. Open that file and you'll see the full history. This is what the /audit/logs endpoint and the UI read from.
  2. Forwarded to an external system, if you turn it on. Set AUDIT_SINK_URL in .env to a webhook or SIEM address and each record is also POSTed there. This happens on a background thread — "fire and forget" with a few retries — so a slow or broken sink never slows down or breaks the actual AI call. Code: backend/src/sink.py. Leave the URL blank to disable it (the default).

A single audit record looks roughly like this (shortened):

{
  "log_id": "8bd5afea-…",
  "emp_id": "EMP-0001",   "name": "Ali Nawaz",
  "vendor": "openai",     "provider": "openai",
  "model": "gpt-4o-mini", "endpoint": "/v1/call_llm",
  "request_payload":  { …already cleaned by the interceptor… },
  "response_payload": { …the AI's reply… },
  "request_guardrail":  { "decision": "allow", "findings": [] },
  "response_guardrail": { "decision": "allow", "findings": [] },
  "status_code": 200,  "latency_ms": 2023.71,

09 Keys, auth & rate limits

There are two completely separate kinds of access. Don't mix them up. Code: backend/src/security.py and backend/src/ratelimit.py.

Developer accessAdmin access
WhoApps calling the AIPeople running the system
HeaderAuthorization: Bearer sk-guard-…X-Admin-Key: …
Protects/v1/call_llm/admin/* and /audit/*
How manyOne unique key per developerOne shared key for all admins
Stored asSHA-256 hash in keys.jsonA single value in .env
Dev-mode gotcha

If ADMIN_API_KEY is left blank, the admin and audit routes stay wide open — anyone can create developers or read every log. That's fine on your laptop, but the server logs a warning at startup, and you must set the key (and the frontend's matching VITE_ADMIN_KEY) before deploying anywhere other people can reach.

Rate limiting

Each developer is capped at RATE_LIMIT_PER_MINUTE calls to /v1/call_llm (default 60), counted with a rolling 60-second window. Go over and you get 429 plus a Retry-After header telling you how many seconds to wait. Set the value to 0 to switch limiting off. (It's in-memory, so it counts per running server process.)

10 Running it yourself

Three parts, three terminals. You really only need the backend to have a working gateway; the two UIs are optional conveniences.

1 · The backend (required)

cd backend
# one-time setup
python -m venv venv
venv\Scripts\pip install -r requirements.txt
# run it
venv\Scripts\python.exe -m uvicorn src.main:app --reload --port 8000

Now the gateway is live at http://localhost:8000. Check /health or open the auto-docs at /docs.

2 · The React admin UI (optional)

cd frontend
npm install
npm run dev        # opens on http://localhost:5173

Three pages: Developers (register + list), Guardrail Policy (edit the rulebook), Audit Logs (browse history).

3 · The Streamlit console (optional)

cd streamlit_ui
pip install -r requirements.txt
streamlit run app.py

Same admin features, plus a Call LLM tab where you can paste a Bearer key and fire a real request to test the whole pipeline end to end.

Quick sanity test with no UI at all

The backend/tests/ folder has three self-contained scripts (test_1_developer_alice.py, …bob…, …carol…). With the server running, each one registers its own developer, makes a real call, and re-reads the audit log to prove the call was recorded. There's also a full offline test suite:

cd backend
venv\Scripts\python.exe -m pytest -q   # no network — providers are faked

Handle this file with care

Your backend/.env holds a real, live secret (ADMIN_API_KEY) — never paste its contents into chat, screenshots, tickets, or a shared document, and never commit it to git. Note what's not in there anymore: no OpenAI/Anthropic/Qwen key. This guide deliberately shows only placeholders like sk-guard-YOUR_DEV_KEY and sk-YOUR_OWN_OPENAI_KEY for that reason.
